# Rover: Moonwater's rules

Rover is the language a person writes what the machine does in: when the
lid closes, sleep; when a game goes full screen, hold the processor's
latency down; when the power key is pressed, power off. It is named for
the moon buggy, the Lunar Roving Vehicle. A rule file ends in `.rover`,
and the verb is `moonwater rover`.

A rule is compiled once, when it is loaded, into a flat binary table. An
event is then answered by walking that table: no text is read, nothing is
allocated, and every walk ends in a number of steps the table fixes. A
rule whose event, conditions and actions are all the kernel's runs inside
the kernel module, at the event, and its actions are direct kernel calls.
The rest run in the process that owns their event, in-process, and a
kernel rule's userspace actions reach their owner through one ring.

The same text is the program, the graph Settings draws, and what
`moonwater rover show` prints. One schema, generated from the code, names
every event, state, function and tool a rule may use; the compiler and
the Settings palette both read it.

## A rule file

```
# Sleep when the lid closes on battery; with a screen plugged in, only
# the built-in panel goes dark.
rule lid-sleep
	about "Sleep when the lid closes on battery"
	on lid close
	if power.source == battery
	if display.external == 0
	do suspend
	else
	do display off

rule game-latency
	about "Hold the processor awake while a game is full screen"
	on fullscreen on steam_app_*
	do latency 20us

rule late-dim
	on lid open
	if clock between 22:00 06:00
	do backlight 30%
```

The file is lines. A line's first word is its keyword and the words after
it are that keyword's arguments, typed by the schema. A rule is a `rule`
line at depth 0 and the lines one tab deeper; the next line at depth 0
ends it. Indentation is tabs only: a line that starts with a space is
refused, because a space and a tab look alike and would mean different
depths.

A `#` line is a note. It belongs to the statement after it, is kept in
the table, and is printed back above that statement. A `#` after a
statement's words is a note on that statement, printed back above it.

### Statements

A rule's statements come in this order, and the compiler refuses any
other: the header (`about`, the trigger, then the options `place`,
`limit`, `once`, `off` and `take`, each at most once and in that order), then the
conditions, then the actions, then `else` and the actions after it. One
order is what makes the printed text the text that was read, and the
table it compiles to the same table, byte for byte.

| Statement | Meaning |
|---|---|
| `rule NAME` | A rule. NAME is `[a-z0-9._-]`, at most 48 bytes, unique in the set loaded together. |
| `about "TEXT"` | What the rule is for, in a person's words. Settings shows it on the event node. |
| `on EVENT [FIELD ...]` | Fire on this event. Each word after the event's name is a value its fields must have, in the fields' order; a word field's value may be a pattern. |
| `when CONDITION` | Fire on the rising edge of a condition over states: when it becomes true, not while it stays true. |
| `every DURATION` | Fire every DURATION, a second or longer, by the runner's clock. |
| `at CLOCK` | Fire at that minute of every day, in the machine's zone. |
| `place kernel` / `place user` | Where the rule must run. Unsaid, the compiler places it (below); said, a rule that cannot run there is refused. |
| `limit DURATION` | Fire at most once in DURATION, whole milliseconds. A firing inside the window is dropped and counted. |
| `once` | Fire once per load of the table, its then actions or its else actions, whichever comes first. |
| `off` | Compiled, checked and shown, but never fired. |
| `take` | The event is the rule's: when the rule fires, the kernel drops the event before any reader sees it (evdev, the console, the compositor). A key taken on its way down is taken on its repeats and its way up. Only a rule the kernel runs can take, so `take` is a `place kernel` the rule must meet; it means something for the key and button events, the ones the input core can drop. |
| `if CONDITION` | A condition. Every `if` line must hold; when one does not, the `else` actions run instead. |
| `do PRIMITIVE [ARG ...]` | A primitive: one of Moonwater's mechanisms. |
| `set SWITCH VALUE` | One of the machine's switches, its value typed by the switch: `set brightness 30%`, `set power powersave`, `set cpu boost off`, `set cpu smt on`, `set charge limit 80`, `set airplane on`. |
| `run SCRIPT [ARG ...]` | A POSIX script leaf, run in userspace, off the fast path. |
| `tool TOOL [ARG ...]` | One of the shell's built-in tools a rule may run (class any in the schema), as a child of the runner's: `/shell` under the tool's name, as root. |
| `emit cue NAME` | Post the event `cue NAME`, which another rule's `on cue NAME` hears. |
| `else` | The actions after it run when a condition did not hold. |

A rule has exactly one trigger, at least one action before any `else`,
and at least one after an `else`.

### Conditions

```
CONDITION  := TERM ( or TERM )*
TERM       := COMPARISON ( and COMPARISON )*
COMPARISON := OPERAND [ OP OPERAND | between OPERAND OPERAND ]
OPERAND    := STATE | $FIELD | CALL | LITERAL
CALL       := NAME ( OPERAND , ... )
OP         := == != < <= > >= ~ !~
```

`and` binds tighter than `or`; there are no parentheses and no `not`.
Every `if` line is one CONDITION and the lines are joined by and.

- `STATE` is a state's name (`power.source`, `battery.percent`).
- `$FIELD` is a field of the event that fired (`$app`).
- `CALL` is a function of the schema, a lib.c routine with value
  arguments (`string_length($app) > 12`). Its arguments are operands but
  never calls: there is no nesting.
- A comparison with no OP asks whether a number, a call's answer, or an
  on/off state is nonzero (`if dock`, `if headphone`).
- `between A B` holds for A ≤ x ≤ B; for clock times, B before A wraps
  past midnight (`clock between 22:00 06:00`).
- `~` and `!~` take a pattern on the right: `*` is any run of bytes, `?`
  is one byte, and every other byte is itself.

At least one side of a comparison is a state, a field or a call; a
literal takes that side's type, and a literal that is not of it is
refused (`battery.percent > tall` is refused at compile).

### The trigger

`on EVENT` names an event of the schema by its words (`on lid close`, `on
key power`, `on fullscreen on`). Each word after the name is a filter on
the event's next field: `on chord super+space`, `on fullscreen on
steam_app_*`. A filter is an equality, or a match for a word field whose
value holds `*` or `?`.

`when` takes a condition over states and calls only: an event's fields
are not states. The compiler records which states it reads, and the rule
is looked at again only when one of those changes. A `when` rule's whole
condition is its `when` line and its `if` lines together: its actions run
when that becomes true, and its `else` actions when it stops being true.
Loading a table is every state changing at once, so a `when` rule that
already holds fires then.

An `on` rule whose filter does not match was not fired at all: its `else`
runs only when the event is its own and an `if` did not hold.

## Services

A service is a long-lived program the runner keeps up: the session bus,
the sound server, the compositor. It is a block of its own, beside the
rules, and a file's services come before its rules.

```
service bus
	about "The session bus"
	run /sessionbus
	ready /run/moonwater/bus
	log /run/moonwater/bus.log
	if canvas == on

service compositor
	run /compositor -u 3
	needs bus
	ready /run/moonwater/windows
	if canvas == on and setting.desktop == on

rule desktop-rest
	on service failed compositor
	do desktop rest
```

| Statement | Meaning |
|---|---|
| `service NAME` | A service, named as a rule is, unique among the services loaded together. |
| `about "TEXT"` | What it is, in a person's words. |
| `run PATH [WORD ...]` | The program, by its absolute path, and its words, each one argument, none read again by a shell. |
| `needs NAME ...` | Up to four services above this one, which must be up before it is started. Naming only a service above keeps needs free of cycles. |
| `ready PATH` | The file or socket whose being there means the service is up. A service with no `ready` is up once it has started. |
| `log PATH` | Where its output goes; unsaid, the kernel's log, each line its name first. |
| `restart WAIT [WAIT [WAIT]]` | The waits before it is started again after its first, second and third short life; a wait not said is the one before it. Unsaid, `restart 0s 500ms 2s`. |
| `give-up LIVES under DURATION` | A life shorter than DURATION is short; LIVES short lives in a row and it is given up, and a life of DURATION or more puts the count back to nothing. Unsaid, `give-up 4 under 30s`. |
| `off` | Compiled and checked, but never started. |
| `if CONDITION` | Started while every `if` line holds, over states and settings, never an event's fields; stopped when one stops holding. |

The statements go in that order, each at most once but the `if` lines.
The policy unsaid is what the machine script's bus, audio and desktop
supervisors did: start again at once, then after half a second, then
after two, and give up after four short lives, a run of thirty seconds
putting the count back.

A service's life is told as events, which rules hear: `service up NAME`
when it is ready, `service down NAME` when it ended, and `service failed
NAME` when it was given up. What follows a failure is a rule's, as
`desktop-rest` above turns the desktop off for the text console, which is
what the script's desktop supervisor did by hand. The primitives `start
NAME`, `stop NAME` and `restart NAME` ask the runner for one by its name.

### Readiness and order

`ready` turns waiting into an event. The script polled for a file every
two thousandths of a second and then every twentieth (`desktop_wait_for`),
read a line down a FIFO the compositor was handed (`compositor.up`), and
held the desktop's programs back until boot's verdict (`desktop_settled`);
a rule says `on service up compositor` instead, and is fired once, when
the compositor's ready path is there.

The runner keeps this order, so a rule never sees a service half started:

1. A service is started only when its `if` lines hold and every service it
   `needs` is up; one whose needs are not up waits, and is started the
   moment the last of them is.
2. `service up NAME` is posted when NAME's ready path is there, watched by
   inotify on its directory and not polled, or at its start when it names
   none. It is posted once a life.
3. Services that need NAME are started before the rules on `service up
   NAME` are fired, so a rule hears a service up with what it needs up too.
4. `service down NAME` is posted when the program ended, before it is
   started again or given up; `service failed NAME` after the last life,
   once.
5. A state that stops a service's `if` stops the service and every service
   that needs it, dependents first, each waited for (TERM, then KILL after
   three seconds) before anything that the same change starts is started.
   That is the stop before start the desktop's hand-over needs.

## Types

Every state, event field, primitive argument and function parameter has
one of these types, and every literal is read as the type the other side
asks for.

| Type | Literals | Held as |
|---|---|---|
| `int` | `0`, `-3`, `12`; a range from the schema (`int 0 16`) | a signed 64-bit number |
| `percent` | `30%`, `12.5%`, from 0% to 100% | hundredths: `30%` is 3000 |
| `duration` | `20us`, `500ms`, `2s`, `1.5s`, `5m`, `1h`; at most 24h | nanoseconds |
| `clock` | `06:00`, `22:30`; 00:00 to 23:59 | minutes since midnight |
| `enum` | one of the schema's words (`ac`, `battery`) | the word's index |
| `onoff` | `off`, `on` | 0, 1: the enum with exactly those two words |
| `weekday` | `mon` `tue` `wed` `thu` `fri` `sat` `sun` | 0 to 6, Monday 0 |
| `chord` | `ctrl+alt+delete`, `super+space`, `shift+f10` | the modifiers and Linux's key number |
| `word` | `firefox`, `steam_app_*`, `"two words"` | bytes, at most 62 |
| `text` | `"Sleep when the lid closes"` | bytes, at most 255, for `about` and messages |

A chord's modifiers are `ctrl`, `alt`, `shift` and `super`, in any order
and printed in that one. Its key is a letter, a digit, `f1` to `f12`, or
one of `escape space enter tab backspace delete insert home end pageup
pagedown up down left right print`.

The printer writes every literal in one spelling: the largest whole unit
for a duration (`1500ms`, not `1.5s`), two digits for a clock, the
schema's word for an enum. Compiling the printed text gives the same
table, byte for byte.

## The schema

The schema is the vocabulary, as records, one per line, in the same
`key=value` form `moonwater` answers queries with.
`moonwater rover schema` prints it, and Settings' palette is built from
that.

```
event id=5 name="lid close" source=kernel
event id=64 name=chord source=desktop fields=chord:chord
state name=power.source page=kernel type=enum choices=ac,battery
primitive id=3 name=suspend runs=kernel class=any bounded=yes
primitive id=8 name="radio on" runs=kernel class=deliberate bounded=yes args=which:enum:wifi,bluetooth,all
function name=string_length args=s returns=int kernel=yes bounded=yes
tool name=grep runs=user bounded=no
```

A record's list of fields or arguments is separated by `;`, since an
enum's words are separated by `,`.

It is generated, not written beside the code, wherever the code already
says it:

- **Kernel events** come from spark's event table (`spark_bind_event_name`
  in `src/moonwater/spark.c`), with spark's own ids, so the kernel's event
  is its rover id and no second table maps one to the other. The four
  stop and sleep keys are spelled as keys: `key power`, `key sleep`,
  `key reset`, `key ctrl-alt-delete`. The rest take spark's name with the
  underscore a space (`lid close`, `brightness up`, `canvas on`).
- **Functions** are lib.c's routines: those the inventory lists on all
  three machines whose prototype is `PURE` or `CONST` and whose arguments
  and answer are values. A `const_string` or `string_address` is a word
  argument; an `address_any` or a word followed by a `positive` named
  `size` or `length` is one byte-buffer argument, its bytes and its length
  (a length a rule could set past the word's end is never one it can
  give); the integer types and `bool` are `int`. A routine with any other
  argument (an out pointer, a table, a writer, a float) or answering a
  pointer is not one: rover hands a function values and gets a number
  back, never an address. `kernel=yes` is a routine whose prototype and,
  on every machine, a body stand outside `#ifndef KERNEL_MODE`.
- **An integer argument's range** is the one thing about a routine the
  code does not say: a selector past its cases, a byte past 255. A routine
  with an integer argument is bound only once `schema.list` has a
  `function` row for it, giving each such argument `PARAM:LOW:HIGH` or
  saying `total`; the evaluator holds the argument to that range when it
  calls. A new routine with an integer argument stays out until somebody
  writes its row (`test/rover_schema.py --why` lists what is left out and
  why).
- **Tools** are the shell's built-in tools, read from `src/sh/tools.inc`.
- **States, userspace events and primitives** are written by hand in
  `src/rover/schema.list`, because nothing in the code says them yet:
  which word means what, and how dangerous it is.

`test/rover_schema.py` writes `src/rover/schema.inc` from those, and
`--check` says when it is stale. The schema has a hash, FNV-1a over the
records `moonwater rover schema` prints; a table carries the hash it was
compiled against, and a table of another schema is refused at load. Ids
of events and primitives are kept forever: one is never given to another.

| Source | Events, with their fields |

| kernel (the module's hooks, ids 23–44, written in `schema.list`) | `key down` and `key up` (chord: every key, with the modifiers held), `mouse down` and `mouse up` (button: left right middle side extra forward back task), `pad down` and `pad up` (button: south east c north west z tl tr tl2 tr2 select start mode thumbl thumbr up down left right), `touch down`, `touch up`, `switch on` and `switch off` (which: every EV_SW switch, Linux's order), `power ac`, `power battery`, `battery` (percent, state), `usb added` and `usb removed` (class, vendor, product: int, port: word), `input added` and `input removed` (kind: keyboard mouse touchpad touchscreen pad tablet switch other, name: word), `display connected` and `display disconnected` (connector: word), `link up` and `link down` (interface: word), `sleep` |

### States

| Page | States |
|---|---|
| kernel | `lid` (open, closed), `power.source` (ac, battery), `battery.percent` (percent), `battery.state` (unknown, charging, discharging, full, not-charging), `headphone`, `dock`, `tablet`, `canvas` (onoff), `display.count`, `display.external` (int 0 16: the screens connected, and those that are not the machine's own panel), `usb.count` (int 0 255, root hubs not counted), `net.link` (int 0 64: links with a carrier, loopback not counted) |
| desktop | `window.fullscreen` (onoff), `window.app` (word) |
| the clock | `clock` (clock) and `weekday` (weekday), from the event's time and the page's zone offset |
| kernel | `boot.NAME`, a word: the value of `moonwater.NAME=` on the kernel's command line (`boot.desktop`, `boot.early`, `boot.cursor_plane`), one for each such argument the sources ask for |
| settings | `setting.NAME`, one for every plain row of the Settings registry (`src/sh/registry.c`), NAME its verb's words joined by dots (`setting.canvas.gpu`, `setting.audio.server`, `setting.keyboard.onscreen`) |

A state lives at a fixed offset of a page. The kernel's page is one page
of the module's memory that the kernel writes as the events arrive and
userspace maps read-only; the desktop's page is the compositor's own; the
settings page is the runner's, which it fills from the files the rows
keep and writes again on each change, and which the desktop maps too.

The settings and boot states are generated. A registry row's type is its
row's: a number row (`.type = SETTING_NUMBER`) is an int between its
`.low` and `.high`, a switch is onoff, a choice of plain words is an
enum of them in the row's order, and anything else (a colour, a font, a
name) is a word. A row added to the registry is a state the next time the
schema is generated; there is no second list. `on setting NAME` (a runner
event, its field the row's name without `setting.`) fires when the row
changes.

A rule's 64-bit mask of the states its conditions read gives a state the
bit of its number modulo 62 (the last two are the clock's and the
weekday's), since there are more states than bits: two states that share
a bit cost a `when` rule a look at a change it does not read, and never
miss one, since its edge is the condition asked again. A comparison over
the settings page is never the walker's, which picks between the first
two pages; the C asks it.

### Switches

| Switch | Type | Notes |
|---|---|---|
| `brightness` | percent | the screen's backlight, as `moonwater brightness` |
| `power` | enum: tune.c's profiles (`performance`, `balanced`, `powersave`) | as `moonwater power` |
| `cpu boost`, `cpu smt` | onoff | as `moonwater cpu boost`, `moonwater cpu smt` |
| `charge limit` | int 20 to 100 | where the battery stops charging, in percent |
| `airplane` | onoff, `off` deliberate | every radio off; turning them back on is a person's |

A switch's value that raises the machine's exposure is deliberate, as a
primitive can be: a rule may set airplane on, never off, and takes a
constant for it, so no state can carry it there. The switches are rows of
`schema.list`, and the power profiles' words are tune.c's own table. The
tune verbs keep their own parsing: each takes more than one value (a
relative brightness, a battery's name, `limit off`, the radios airplane
keeps), so one table under both would change what each verb accepts.

## Safety

Each primitive has a class.

- **any**: a rule may use it.
- **lower-only**: it lowers the machine's exposure, and a rule may use it.
  Its raising counterpart is a primitive of its own (`radio off` has
  `radio on`, `usb lock` has `usb allow`), so the direction is the
  primitive and no argument can turn one into the other.
- **deliberate**: never from a rule. Turning a radio on, letting a device
  in or lowering the firewall takes a person at Settings or at a
  terminal. The schema lists these so the palette can show them, and the
  compiler refuses them with that reason; the loader refuses them again.

A rule can never raise exposure. That keeps the air gap that radios off by
default, the USB lock and the firewall's tiers give.

**Tools have a class too.** A tool a rule may run is one that reads and
says: `cat`, `grep`, `logger`, the sums, `ls`, `stat` (schema.list's
`tools-any` rows). Every other tool is deliberate, and the compiler and the
loader refuse it: one that writes a file (`cp`, `dd`, `tee`, `sort -o`,
which reaches `/sys` and `/proc` as well), one that runs another program
(`env`, `find -exec`, `xargs`, `nice`, `timeout`, `unshare`), one that sets
the machine (`rfkill unblock`, `ip link set up`, `mount`, `chroot`,
`ctrlaltdel`, `date`, `hostname`, `kill`) and `moonwater` itself. A new
tool is deliberate until it is listed.

**A `run` script is root, and outside the promise.** The script does
whatever its text says, as root; the classes say nothing of it. That is why
only root may write one: the person's scripts are read from
`/root/rules/scripts`, which must be root's and 0700, and the image's from
`/lib/moonwater/rules/scripts`, which must be root's and written by root
alone; the runner looks at the directory and the file each time it runs one
(the file regular, root's, written by root alone, not a link), and runs
nothing from a directory that fails.

**What root runs is the rule file's own words.** The runner is root, and an
event's fields and the desktop's states are what other programs say: a
Wayland client chooses its app id, a USB device its vendor and a keyboard
its name. So the compiler refuses a field (`$app`, `$name`) or a state as
any argument of `run` (the script's words), `tool` (its operands), `open`
(the program and its words) and `emit cue` (the cue's name, which picks the
rules that run next). A field goes only where it is data: a condition, a
`log` or `notify` text, a service's name for `start`, `stop` and `restart`
(which names one of the table's services or nothing). The pin's program is
not a field either: `open pin` starts the program of the pin the person
pressed only when it is one the machine knows (a kit program `/NAME` or a
bowl's launcher `/bowls/bin/NAME`, root's and written by root alone), and
never with the window's words.

Each function and action is also **bounded** or not. A primitive is
bounded: the kernel's half queues a request and returns. A function is
bounded: it is pure and linear in its arguments, and every argument a
rule can hand it is at most 255 bytes. A `run` or a `tool` is not
bounded, and neither is evaluated where the event is: it is handed to its
owner.

### Where a rule runs

The compiler places every rule, and the table says where.

1. A kernel event's rule runs in the **kernel** when everything its
   conditions read is the kernel's: kernel states, the clock, its own
   fields, constants, and functions marked `kernel=yes`.
2. A desktop event's rule runs in the **desktop**, in the compositor, which
   maps the kernel's page too.
3. A `when` rule over kernel states only runs in the kernel; over any
   desktop state, in the desktop; over the clock or the weekday, in the
   runner, which asks it again at every minute (and at every new day for
   the weekday), since no page changes with the time.
4. Anything else, and every `cue` rule, runs in the **runner**, the
   userspace end of the kernel's ring: a kernel event whose rule reads a
   desktop state is handed to the runner, which evaluates it there.

`place kernel` makes the first rule a demand: a rule that cannot run in
the kernel is refused with the reason (a desktop state, a userspace-only
function), where unsaid it would have gone to the runner. `place user`
keeps a kernel event's rule out of the kernel.

An action runs where its primitive does. A kernel rule's kernel
primitives are direct calls; its `run`, `tool`, `emit` and desktop
primitives go through the ring to their owner. A userspace rule's kernel
primitive is the same mechanism asked through its ioctl.

### What the loader checks

The kernel does not trust the compiler. A table is checked whole before it
is used, and a table that fails any check is refused and never loaded;
the table before it stays.

- **Size and shape**: at most 64 KiB; the magic, the version and the
  schema's hash; every count and offset inside the table; every section
  where the counts put it; every string inside the pool and terminated.
- **Every reference in range**: event ids, state offsets inside their
  page and aligned to their type, field numbers below four, call and
  argument runs inside their sections, function ids with the argument
  count and types the function takes.
- **Kernel rules**: every operand is the kernel's (no desktop state, no
  userspace-only function), and every primitive a kernel rule calls in
  the kernel is in the kernel's list.
- **The allowlist**: a primitive of class deliberate is refused anywhere;
  every argument is in its type's range (a percent 0 to 100%, a duration
  at most 24h, an enum below its count).
- **Cues**: an `emit` chain is cut at depth 4 when it runs, and the
  compiler refuses a rule that emits its own cue with no condition.

**Safe mode** loads the image's own rules and ignores the person's
files: `moonwater.safe=1` on the kernel's command line, or two loads in a
row that did not stand a minute. Every load counts itself in
`/root/rules/.boots` before the kernel has it, the runner's at its start
and `moonwater rover load`'s alike, and the runner puts the count back to
0 once the table it has has been live for a minute, so a person's rule
that stops or wedges the machine soon after it loads twice is not loaded a
third time. The image's rules are carried in the program itself (compiled
from `src/rover/examples`), so safe mode reads no file at all; a set with
the person's files that does not compile as a whole is tried again as the
image's alone.

**The floor**: the power key and Ctrl-Alt-Delete always work. With no
table loaded, or with a table whose rule for them is refused or turned
off, the kernel powers off or reboots as it does today; a second press
within ten seconds always takes the kernel's default. `take` is where the
floor is kept, in one place, the kernel's input filter, which is the one
pipeline every key goes through (rover's rules, then the bindings, which
hear what the rules let through):

- A `key power`, `key reset` or `key ctrl-alt-delete` rule that takes a
  press may take it only when the press before it was not taken inside
  ten seconds, timed on the kernel's own clock with a signed difference,
  so the second press goes on to the bindings and stops the machine as it
  always did (`status` counts it as floor).
- A `key down power`, `key down` with no key, or any other key rule fires
  on a stop key but never takes it: the stop keys are taken only through
  their own events.
- The bindings' Ctrl and Alt follow the physical keys whatever a rule
  took, so a rule that takes Ctrl or Alt cannot leave Ctrl-Alt-Delete with
  no modifier held.
- A rule's `poweroff` and `reboot` are never a slot of the kernel's queue:
  they have a work item of their own, so a wedged job cannot hold them
  and a full queue cannot lose them, and a line that never returns is cut
  by a watchdog that stops the machine sixty seconds after the request.
- A grab (EVIOCGRAB) does not blind it: kernel/patch/apply makes the input
  core run its filters ahead of a grab, so the rules, the floor and the
  bindings hear a grabbed keyboard, and what they take the grab does not.
- A key device whose driver will not open is deaf, to the rules and the
  bindings alike, as it always was; the kernel's log says so when it
  happens. It is outside the floor.

### Files

The image's rules are the program's own, the same files as
`/lib/moonwater/rules/*.rover` holds to read and copy, and the person's are
`/root/rules/*.rover`. A file in `/root/rules` replaces the image's file
of the same name, and an empty one masks it; one that may not be read or
does not compile is said with its line, and the image's of its name
stands. A `run` script is
`/root/rules/scripts/NAME`, else the image's of that name. Files under
`/root/rules` are read only if they are regular, owned by root, not
writable by group or others, and at most 64 KiB, as the machine script was
read today.

## The kernel

The module's half is `src/moonwater/rules.c`, built into the core with
`rover.c` under `KERNEL_MODE` (the walkers included; the key scan is the
word loop, since lib.c keeps no kernel body of it).

**The load.** `ROVER_IOCTL` on `/dev/spark` (`_IOWR('s', 19)`, a
512-byte request; LOAD, UNLOAD and DO are CAP_SYS_ADMIN's, STATUS is
anyone's, but its counts and timings are CAP_SYS_ADMIN's alone, since with
a key rule loaded they are keystrokes counted; anyone else is told the
live table and its rules, and a poll by anyone else is never readable). LOAD copies the table in, runs `rover_check` over the whole of
it, makes its run records, and swaps it in under the rules' lock with
`rcu_assign_pointer`; the table before it is freed after a grace period.
A refused table is answered with the reason and the rule, and the live
one stays. A load is every state changing at once, so the `when` rules
that hold fire at it. The machine process loads the rule files at its
start; `moonwater rover load` does it by hand.

**The state page.** One 4 KiB page the module writes as its events
arrive: its head (version, a sequence odd while a write is in flight, the
zone's offset from `sys_tz`), then the kernel states at the schema's
offsets. `/dev/spark` mapped read-only from offset 0 is the page, for
anyone; a map can never be made writable. A new device's switches are
read into it at connect, and the supplies at start, so a lid closed at
boot reads closed before it moves.

**The hooks**, each at the earliest point the kernel offers its event:

| Event | Where it is heard | Context |
|---|---|---|
| keys, buttons, switches (the ACPI buttons are input devices) | the input core's filter: the key watch is an `input_handler` with `.filter`, which the core puts at the head of each device's handles, ahead of evdev and the console's keyboard | the device's event lock, interrupts off |
| `input added`, `input removed` | the handler's connect and disconnect | the input core's mutex |
| `power ac`, `power battery`, `battery` | `power_supply_reg_notifier`, as a supply's change work runs; every supply read again, no polling | process |
| `usb added`, `usb removed` | `usb_register_notify`, once the device is configured (so its first interface's class is known) | process |
| `display connected`, `display disconnected`, the counts | Canvas's DRM client hotplug, after the probe helper set each connector's status | process |
| `link up`, `link down`, `net.link` | the netdevice notifier: a carrier with the link running, in the first namespace | RTNL |
| `sleep`, `resume` | the pm notifier, PM_SUSPEND_PREPARE and PM_POST_SUSPEND | process |
| `canvas on`, `canvas off` | `moonwater_bind_fire`, which Canvas calls | process |

**Where an input device comes from.** Only the machine's own devices are
the rules': one whose chain of parents in the kernel ends at a real bus's
device (a platform, ACPI, a PCI root; a virtual machine's virtio and USB
devices are its machine's own). A program's device (uinput, uhid, which
sysfs puts under `devices/virtual`) fires no rule, writes no state (a
program's lid switch closes no lid) and is never taken, and its switches
and stop keys reach no binding either, so a program in the input group
cannot stop the machine or put it to sleep. It is the compositor's rule
(WINDOW_EVENT_VIRTUAL), asked of the kernel's devices themselves; a
program sets a uinput device's bus, name and phys, so none of those is
asked. Its coming and going is no `input added` or `input removed` either.
Its other keys go on to every reader as before.

Not heard, and why: rfkill has no in-kernel listener (a change goes to
`/dev/rfkill` only; the rfkill keys and `SW_RFKILL_ALL` are heard as keys
and switches), and a thermal trip reaches only netlink and a tracepoint
the image does not build.

**An event** takes the rules' raw spinlock once: the states it changes
are written, the kernel's rules of its event fired by `rover_fire`, and
then the `when` rules over what changed by `rover_edges`. An event no
rule has is a bit test in the live table before the lock is taken, and
a mouse moving costs one compare of its type.

**Actions.** A kernel rule's kernel primitive is never run in the hook:
its arguments are resolved there (a text copied out), it goes into a
queue of sixteen, an `irq_work` is raised, and its handler queues a work
item that does it: `log` to the kernel's log, `latency` and `latency off`
as a cpu latency QoS request, `backlight` through the backlight class
(else `moonwater brightness`), and `poweroff`, `reboot`, `suspend`
(`moonwater sleep`), `radio off` (`moonwater wifi off`, `bluetooth off` or
`airplane on`) and `usb lock` (`moonwater device lock`) as the bindings
run a line, `poweroff` and `reboot` stopping the machine anyway if the
line fails. A full queue drops the action and counts it (`lost`).

**The ring.** Every rule the kernel fires is one record in a ring of 256
records of 128 bytes, after the state page in the same map (the ring is
CAP_SYS_ADMIN's: a key rule's ring is a key log), and so is every kernel
event a runner's rule waits for. A record is the event (its id, its
time, its fields, its one word field copied), the rule and its run of
actions, the load it is of, whether it was taken, and when the kernel
decided. One producer writes it under the lock, its sequence last; a
reader that finds another sequence was overtaken. `read` on `/dev/spark`
answers the head and blocks until it moves; `poll` says readable when it
has moved past what the descriptor read.

**The consumer** is the runner (`src/rover/runner.c`), the machine
process: its wait (`MOONWATER_IOCTL_MACHINE`, WAIT) also answers
`MOONWATER_ROVER` (255) when the ring has records a userspace owner acts
on, and the runner reads them to the head. A kernel rule's hit has its
actions that are not the kernel's done there (its kernel primitives the
kernel already queued), and an event record is asked of the runner's
rules, which read a copy of the kernel's page (taken whole between two
even sequences, the boot words and the zone kept over it). The page is
looked at every turn of the runner's loop too, so a runner's `when` rule
over a kernel state hears its change at the next wake. A record of
another load than the runner's is a table loaded by hand (`moonwater
rover load`): the runner compiles the same files and takes that table,
its services kept by name. A runner rule's kernel primitive is asked
through DO. The image's spark bindings run beside it for an event no
rule takes.

**Measured** in an x86_64 guest under QEMU's TCG on the Mac (no KVM on
box, no x86 virtualisation on Apple silicon), so every figure is
emulated, several times what a machine takes; the pairs are what is
claimed. Forty F10 presses typed through QMP into a USB keyboard, a
`key down f10` rule in the kernel, heard at once by `moonwater rover
watch` on the ring and by an evdev reader (the compositor's first hop
today, `EVIOCSCLOCKID` monotonic, the same timestamp): the event to the
rule's decision 25.4 µs on average (11 to 15 µs typical, 464 µs at
worst); the event to the ring's reader awake 284 µs on average, 1.08 ms
at worst; the event to the evdev reader awake 598 µs on average, 2.98 ms
at worst. Today's chord path goes on from that evdev hop to the
compositor's key table, the `keys.fire` FIFO and the shell function, so
rover's ring is ahead of it before the compositor has read the key.
Natively the evaluator's part is `BENCH_rover`'s nanoseconds (above).
In the same guest a taken F9 reached no evdev reader, three presses, and
the power key taken once (`system_powerdown`) did not stop the machine;
the second, three seconds later, went to the bindings and powered off.
`usb added`, `input added`, a `when usb.count >= 3` edge and `link down`
and `link up` (QMP `set_link`) each fired their rule.

## The table

The compiler's output and the evaluator's input. All numbers are little
endian, all offsets are bytes from the start of the table, and the table
is at most 64 KiB. The sections follow the head in this order, each
starting at a multiple of eight, so the counts fix every offset and the
checker compares the size it computes with the size the head says.

| Section | Entry | Bytes |
|---|---|---|
| head | magic `ROVR`, version 3, the services' count, size, schema hash, the six counts, the pool's size | 32 |
| rules | one per rule | 40 each |
| services | one per service | 56 each |
| order | the rules' numbers sorted by event, so an event's rules are a run | 2 each |
| keys | for each slot of order, the number its rule's first filter asks field 0 to be, or `0xffffffff` for any | 4 each |
| index | for each event id below 128: the first entry of its run in order, and how many | 4 × 128 |
| comparisons | one per comparison, a rule's in one run | 16 each |
| calls | a function call: its id, its argument count, four operands | 20 each |
| actions | a rule's then-actions, then its else-actions, in one run | 8 each |
| arguments | an action's arguments, as operands | 4 each |
| notes | a note: its rule (with the top bit, its service), its statement's place, its text | 8 each |
| pool | constants: numbers as 8 aligned bytes; strings as a length of two bytes, the bytes and a NUL | up to the rest |

**A rule** is its event (0 for a `when` rule), where it runs, its flags
(once, off, placed), its run of comparisons and how many of them are the
`on` line's filters, its run of actions and how many are before the
`else`, its limit in milliseconds, its name and about text as pool
offsets, and the states it reads as a 64-bit mask.

**A comparison** is its operator, its type, how it joins the next (and,
or, or the end of its line), its form and three operands; the third is
`between`'s upper bound. The form says how the evaluator asks it: two
number sides (a constant, a state or a field) under `== != < <= > >=` are
the number form, two loads and one compare; anything else is the general
one. The check holds every form, and every key, to what its comparison
and its rule are, so neither can be told apart from the table's own
shape.

**An operand** is four bytes: where the value comes from (a constant, a
state, a field, a call, the clock, the weekday), a byte that is the
state's page or the constant's type, and a 16-bit index: the state's
offset in its page, the field's number, the call's number or the
constant's offset in the pool.

**A service** is its name, ready path, log path and about as pool
words, its run as a run of the arguments (the program's path first, each
a word), its flags (off), its if lines as a run of comparisons, the
services it needs as up to four indices of services before it, the lives
it is given up after, its three waits in milliseconds, the length a life
must have not to be short, and the states its if lines read as a 64-bit
mask. Nothing of it is text a runner has to read: it starts the program
from the words, watches the path, and counts.

**An action** is its kind (`do`, `run`, `tool`, `emit`), who runs it
(kernel, runner, desktop), its id (the primitive, the tool or the event),
and its run of arguments.

### The evaluator

```
rover_fire(table, runs, pages, event, place, hits, room)  ->  how many hits
rover_edges(table, runs, pages, changed, event, place, hits, room)
rover_arguments(table, action, event, pages, values)  ->  how many
```

It takes the checked table, the per-rule run records (when each last
fired, how often, the edge of a `when`), the state pages and an event, and
answers which action runs fire: each hit is a rule and the run of its
actions it chose. It looks up the event's run of rules in the index,
keeps those placed where it is, passes over a rule whose first filter is a
number the event's field is not (every chord rule but the one pressed) at
that one compare, and walks the rest's comparisons once, skipping the rest
of a term that has already failed and of a line that has already held. A
number is one load: the check has proven every constant and state offset
aligned and in range, so the evaluator checks nothing again. The answer
resolves an action's arguments only when its owner asks
(`rover_arguments`). Nothing is allocated, no text is parsed and nothing
loops but over the table's own runs, so the time an event takes is bounded
by the table: by its size, and by its patterns, since a pattern is matched
in time its length times the text's (a `*` restarts it at every byte of
the text, so a 31-byte pattern against a 55-byte name is about 2 µs). For
the kernel, where an event is asked with interrupts off, that bound is a
budget the loader holds (`rover_kernel_fits`, under The kernel): no more
than 16 of the kernel's rules can fire on one event, they queue at most 16
kernel primitives, and asking them costs at most 16384 units of about a
nanosecond, a pattern counted at 64 times its length plus one. A table
past any of the three is refused by the compiler and the loader alike,
with the event named; the same rules placed in userspace (`place user`)
have no such budget.

The same C is the userspace evaluator and, built with `KERNEL_MODE`, the
kernel's.

Two pieces are assembly where it was measured to win:

- **The key scan** of a run of sixteen rules and more is lib.c's
  `memory_first_of_either_u32`: AVX2 and SSE2 on x86_64, NEON on arm64,
  the word loop in a kernel build, which owns no vector register.
- **The walker**, `rover_walk_numbers` in `rover.c` on x86_64 and arm64:
  a short run whose rules' comparisons all have the number form (the
  index marks such a run, and the check holds the mark to the rules) is
  walked by one leaf of scalar assembly, which a kernel build takes too.
  A comparison there is its two loads and one shift of an immediate that
  holds every operator's answer. It takes runs of fewer than eight rules
  on x86_64 and fewer than four on arm64, where it measured faster;
  anything else, and every run on riscv64, is the C. The walker reads
  rover's records by offset, so it lives beside them and not in lib.c,
  and `_Static_assert`s hold every offset it reads.

### What it costs

`BENCH_rover`: the best of a million events a trial, the walker's trials
and the C's taken in turn in one process. x86_64 is box (Ryzen 9 9950X,
one core, measured while a game was running there, so the pairs are the
claim and the absolute numbers are slow); arm64 is the Mac's Lima VM
(Apple silicon). gcc -O2 is the image's compiler; asm is the walker or
lib.c's routine, and C is the same build with them off.

| An event | x86_64 gcc: C, asm | arm64 gcc: C, asm |
|---|---|---|
| `lid close`, no condition: the dispatch | 5.87, 5.80 ns | 5.91, 4.67 ns |
| `lid close`, one condition | 8.74, 8.03 ns | 7.76, 6.50 ns |
| `lid close`, two conditions | 11.2, 10.1 ns | 10.3, 8.20 ns |
| a chord among 4 rules | 9.46, 8.83 ns | 8.64 ns (C) |
| a chord among 8 rules | 10.6 ns (C) | 10.0 ns (C) |
| a chord among 32 rules, lib.c's scan | 12.3 ns | 14.1 ns |
| a chord among 128 rules, lib.c's scan | 16.1 ns | 23.7 ns |
| a pattern on a window's name | 18.3 ns | 16.2 ns |
| a lib.c call on a window's name | 14.5 ns | 14.4 ns |
| a `when` edge | 9.2 ns | 8.6 ns |
| an event no rule has | 0.53 ns | 0.57 ns |

`memory_first_of_either_u32` against the key loop it replaced, C then
asm: 16 keys 4.2, 0.9 ns on x86_64 (AVX2) and 7.8, 4.9 ns on arm64
(NEON); 32 keys 7.1, 1.6 and 15.0, 6.4; 128 keys 25, 3.8 and 61, 14; 1000
keys 212, 27 and 424, 90.

Before this floor (the first evaluator, on an idle box, clang): the
dispatch 3.2 ns, two conditions 9.9, a chord among 32 rules 59 and among
128 228, a pattern 17, an event no rule has 0.82. A file's load, compile
and check, is 1.1 to 2.0 µs once a file; its check alone, as the kernel
runs it, 0.1 to 0.2 µs.

For scale, on the same box: a hook script run for each event is about
514 µs, and a shell function in a long-lived process about 17 µs. A rule
answered by rover is about two thousand times cheaper than the function
and fifty thousand times cheaper than the script, before any action runs.

## The verb

A FILE of `-` is standard input, which is how Settings checks a rule as
it is edited.

```
moonwater rover check FILE ...         compile, refuse with the line and the reason, or say ok
moonwater rover print FILE             the canonical text: what the table says, printed back
moonwater rover compile FILE OUT       the table, written to OUT
moonwater rover show FILE              the graph: event, condition and action nodes and their edges, as records
moonwater rover schema                 the schema's records
moonwater rover test FILE EVENT ... [STATE=VALUE ...]
                                       fire EVENT against the rules with those states, and say what would run
moonwater rover load                   the image's and the person's rule files, compiled into one table and loaded
moonwater rover unload                 the kernel's table cleared
moonwater rover status                 what the kernel's rules did: events, hits, taken, queued, and how fast
moonwater rover state                  the kernel's state page, one state a line
moonwater rover watch [N]              the ring's records as they come (N of them), each with its times
```

`show` prints the graph Settings draws: an event node with one out port, a
condition node with a yes port and a no port for each `if`, and an action
node with a then port for each action, the chain in the text's order. The
layout is computed from that (columns event, conditions, actions), so no
position is ever stored and the text is the only thing saved.
